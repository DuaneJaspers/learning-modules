# Learning Modules — Course Authoring Guide

This repository hosts learning content for the **Modular Learning** Android app — an offline-first, FOSS learning platform with exercises, flashcards, and spaced repetition.

This guide covers everything you need to create a course: the JSON schema, exercise types, scoring, best practices, and common pitfalls.

## Quick Start

```
learning-modules/
├── modules.json           ← canonical index (auto-generated by CI)
├── modules/
│   ├── my-course/
│   │   ├── module.json    ← your course
│   │   └── assets/        ← optional images, audio
│   └── another-course/
│       └── module.json
└── README.md
```

1. Create a directory: `modules/your-course-id/`
2. Write `module.json` (see schema below)
3. Add an entry to `modules.json` with the SHA-256 checksum
4. Open a pull request

## Module Structure

A **module** is a self-contained course. Each module contains:
- **Sections** — top-level chapters (e.g., "Introduction", "Advanced Topics")
- **Lessons** — reading content within a section (Markdown-formatted)
- **Exercises** — interactive questions within a section
- **Assessment** — a final quiz covering the whole module
- **Flashcard Deck** — key terms for spaced repetition review

The student progresses: Section 1 lessons → Section 1 exercises → Section 2 → ... → Final Assessment.

---

## Module JSON Schema

Top-level fields:

```json
{
  "id": "unique-kebab-case-id",
  "title": "Human-Readable Title",
  "description": "1-2 sentence overview of the course.",
  "author": "Your Name or Team",
  "version": "1.0.0",
  "estimatedMinutes": 90,
  "sections": [ ... ],
  "assessment": { ... },
  "flashcardDeck": { ... }
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `id` | string | ✓ | Unique kebab-case identifier. No spaces. |
| `title` | string | ✓ | Display name. |
| `description` | string | ✓ | Shown in module catalog. |
| `author` | string | ✓ | Attribution. |
| `version` | string | ✓ | Semver. Bump when content changes. |
| `estimatedMinutes` | int | ✓ | Approximate completion time. |
| `sections` | array | ✓ | At least one section. |
| `assessment` | object | | Final quiz. Recommended. |
| `flashcardDeck` | object | | Spaced repetition cards. Recommended. |

### Section Schema

```json
{
  "id": "section-1",
  "title": "Section Title",
  "order": 1,
  "lessons": [ ... ],
  "exercises": [ ... ]
}
```

### Lesson Schema

```json
{
  "id": "lesson-1-1",
  "title": "Lesson Title",
  "content": "**Markdown** formatted text with \\n\\n for paragraphs.",
  "order": 1,
  "estimatedMinutes": 5
}
```

**`content`** supports Markdown: `**bold**`, `*italic*`, `### headings`, `1. numbered lists`, `- bullet lists`, `` `inline code` ``, and `\n\n` paragraph breaks.

## Exercise Types

There are **6 exercise types**. Each is identified by its `"type"` field.

Every exercise has these common fields:

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `id` | string | ✓ | Unique within the module. |
| `type` | string | ✓ | One of: `mcq`, `worked_example`, `socratic`, `socratic_ai`, `drag_sequence`, `error_spotting` |
| `prompt` | string | ✓ | The question or instruction shown to the student. |
| `order` | int | ✓ | Display order within the section. |

---

### 1. Multiple Choice (MCQ)

**`"type": "mcq"`**

The simplest exercise type. Pick one correct answer from a list.

```json
{
  "id": "mcq-1",
  "type": "mcq",
  "prompt": "Which cipher operates on fixed-size blocks of data?",
  "order": 1,
  "options": [
    "Caesar cipher",
    "AES",
    "ROT13",
    "Vigenère cipher"
  ],
  "correctIndex": 1,
  "explanation": "AES is a block cipher that operates on 128-bit blocks. The others are substitution ciphers operating on individual characters."
}
```

| Field | Type | Description |
|-------|------|-------------|
| `options` | string[] | 3-6 answer choices. |
| `correctIndex` | int | 0-based index of the correct answer. |
| `explanation` | string | Shown after answering. Explain *why* the answer is correct and why the others are wrong. |

**Tips:**
- Use 4 options (3 distractors + 1 correct) for best discrimination.
- Distractors should be plausible — common misconceptions work well.
- Always include an `explanation` — this is where learning happens.

---

### 2. Worked Example

**`"type": "worked_example"`**

A step-by-step walkthrough where the student fills in a missing part. Great for teaching *process*.

```json
{
  "id": "worked-1",
  "type": "worked_example",
  "prompt": "Complete the deductive argument:",
  "order": 2,
  "steps": [
    {
      "id": "step-1",
      "text": "Premise 1: All reptiles have scales."
    },
    {
      "id": "step-2",
      "text": "Premise 2: ",
      "missingPart": {
        "expectedAnswer": "snakes are reptiles",
        "keywords": ["snakes are reptiles", "snakes", "reptiles"],
        "tolerance": 0.1
      }
    },
    {
      "id": "step-3",
      "text": "Conclusion: Snakes have scales."
    }
  ],
  "hint": "Think about what category snakes belong to."
}
```

| Field | Type | Description |
|-------|------|-------------|
| `steps` | Step[] | Ordered list. Most steps just show `text`. |
| `steps[].missingPart` | object | If set, this step requires student input. |
| `missingPart.expectedAnswer` | string | The ideal answer. |
| `missingPart.keywords` | string[] | Accepted keywords. The student's answer is checked against these. |
| `missingPart.tolerance` | float | For numeric answers, how close the value must be (default: 0.1). |
| `hint` | string | Shown on request. |

**Tips:**
- Use 3-5 steps. At most 1-2 should have `missingPart`.
- The `missingPart` should be the *key insight*, not a trivial detail.
- Include multiple keyword variations (e.g., "snakes are reptiles", "all snakes are reptiles").

### 3. Socratic (Keyword)

**`"type": "socratic"`**

Open-ended question validated by keyword matching. Simpler than Socratic AI — good for factual recall.

```json
{
  "id": "socratic-1",
  "type": "socratic",
  "prompt": "Why is it important for a deductive argument to have true premises?",
  "order": 3,
  "modelAnswer": "A deductive argument guarantees the conclusion only if the premises are actually true. Valid structure alone isn't enough — you need soundness.",
  "keywords": ["true", "soundness", "valid", "premises", "guarantee"],
  "hints": [
    "Consider what happens when the starting facts are wrong.",
    "This is the difference between validity and soundness."
  ]
}
```

| Field | Type | Description |
|-------|------|-------------|
| `modelAnswer` | string | Ideal answer (shown to student after submission). |
| `keywords` | string[] | The student's answer is checked for these. Partial credit if some are missing. |
| `hints` | string[] | Progressive hints shown on request. |

**Scoring:** The validator counts how many keywords appear in the student's answer. Score = `matched / total keywords`. A lightweight stemmer handles word forms ("frequent" matches "frequency").

**Tips:**
- Use for factual/conceptual questions where specific terms matter.
- Include word-form variations if needed ("encrypt", "encrypted", "encryption").
- 3-5 progressive hints: vague → specific → almost-giving-it-away.

---

### 4. Socratic AI (Embedding)

**`"type": "socratic_ai"`**

Open-ended question validated by semantic similarity. The most powerful exercise type — tests *comprehension*, not keyword recall.

```json
{
  "id": "socratic-ai-1",
  "type": "socratic_ai",
  "prompt": "You intercept two encrypted messages. Message A was encrypted with a Caesar cipher, and Message B with AES-256. You only have the ciphertext for both — no key, no plaintext. Explain why you have a realistic chance of reading Message A but not Message B.",
  "order": 4,
  "modelAnswer": "Message A uses a simple letter shift, so every occurrence of the same plaintext letter produces the same ciphertext letter. Statistical patterns are preserved. Message B uses AES which produces output indistinguishable from random noise.",
  "mustInclude": [
    "same plaintext letter produces same ciphertext",
    "statistical patterns preserved",
    "indistinguishable from random",
    "without the key"
  ],
  "niceToHave": [
    "diffusion",
    "fixed-size blocks",
    "frequency counting"
  ],
  "hints": [
    "Think about what happens when you encrypt the letter 'E' ten times in each cipher.",
    "If you looked at a histogram of letter frequencies in each ciphertext, what would you see?"
  ],
  "minScore": 0.55,
  "validationMode": "embedding"
}
```

| Field | Type | Description |
|-------|------|-------------|
| `modelAnswer` | string | Ideal answer. Used for comparison and shown after submission. |
| `mustInclude` | string[] | **Multi-word concepts** that MUST appear in the answer. All must be hit to pass. |
| `niceToHave` | string[] | Bonus concepts. Small score boost (max +10%) but not required. |
| `hints` | string[] | Progressive hints. |
| `minScore` | float | Passing threshold (0.0-1.0). Default: 0.6. |
| `validationMode` | string | `"keyword"` (offline, fast) or `"embedding"` (on-device ML model, semantic). |

#### How Scoring Works

**Keyword mode:** Each `mustInclude` concept is checked via substring + stem matching against the student's answer. Score = `concepts matched / total concepts` + up to 10% bonus from `niceToHave`. To **pass**, the student must hit ALL `mustInclude` concepts AND meet `minScore`.

**Embedding mode (recommended):** Each `mustInclude` concept is converted to a phrase embedding and compared to the student's answer using cosine similarity. This catches paraphrases and synonyms — a student who says "the output looks completely random" will still match "indistinguishable from random".

#### ⚠️ Critical: Writing Good mustInclude Concepts

This is the most important part of authoring a `socratic_ai` exercise. Bad concepts make the exercise either trivially gameable or impossibly strict.

**❌ BAD — Single words that appear in the prompt:**
```json
"mustInclude": ["substitution", "frequency", "mapping"]
```
Problem: The student can just type the prompt's words back and get 100%. This tests echo, not comprehension.

**❌ BAD — Concepts that are too specific:**
```json
"mustInclude": ["AES uses a 128-bit block size with 14 rounds for 256-bit keys"]
```
Problem: The student must parrot an exact sentence. No room for own words.

**✅ GOOD — Multi-word comprehension checkpoints:**
```json
"mustInclude": [
  "same plaintext letter produces same ciphertext",
  "statistical patterns preserved",
  "indistinguishable from random",
  "without the key"
]
```
Why: These are *implications* the student must explain. They can't be guessed from the prompt. They require understanding the mechanism.

#### Concept Design Checklist

- [ ] Can the student pass by typing words from the prompt? → If yes, redesign.
- [ ] Can the student pass by listing single keywords? → If yes, make concepts multi-word.
- [ ] Does each concept represent an *understanding* rather than a *vocabulary word*? → Must be yes.
- [ ] Would a confident expert naturally express this idea in their own words? → Must be yes.
- [ ] Are there 3-5 concepts? (Fewer = too easy, more = too strict) → Aim for 3-5.
- [ ] Does the prompt *avoid* containing the answer words? → Must be yes.

#### Example Scoring Matrix

| Answer | Score | Pass? | Why |
|--------|-------|-------|-----|
| "substitution frequency mapping" | 5% | ✗ | Old keyword approach. Zero multi-word concepts matched. |
| "Caesar is weak, AES is strong" | 0% | ✗ | Vague filler. No concrete concepts. |
| "same letter maps to same letter every time, not sure about AES" | 55% | ✗ | Partial. Hits 2/4 concepts. |
| "same plaintext letter → same ciphertext, patterns preserved, AES looks random, need the key" | 100% | ✓ | All 4 concepts. Own words. |

### 5. Drag-to-Sequence

**`"type": "drag_sequence"`**

Order items by dragging them into the correct sequence. Great for teaching *processes* and *chronology*.

```json
{
  "id": "drag-1",
  "type": "drag_sequence",
  "prompt": "Arrange the steps of evaluating an argument in the correct order:",
  "order": 5,
  "items": [
    { "id": "item-1", "text": "Check if the premises are true" },
    { "id": "item-2", "text": "Identify the conclusion" },
    { "id": "item-3", "text": "Check if the reasoning is valid" },
    { "id": "item-4", "text": "Check for logical fallacies" }
  ],
  "correctOrder": [1, 2, 0, 3]
}
```

| Field | Type | Description |
|-------|------|-------------|
| `items` | SequenceItem[] | The elements to order. |
| `items[].id` | string | Unique within the exercise. |
| `items[].text` | string | Display text for the item. |
| `correctOrder` | int[] | **0-based indices** into `items` in the correct order. |

**Scoring:** The student's order is compared position-by-position against `correctOrder`. Score = `correct positions / total items`.

**⚠️ The `correctOrder` array uses 0-based indices into `items`.** In the example above, `[1, 2, 0, 3]` means: first item-2 ("Identify the conclusion"), then item-3 ("Check reasoning"), then item-1 ("Check premises"), then item-4 ("Check fallacies").

**Tips:**
- Use 4-7 items. Fewer is too easy, more is tedious on mobile.
- Items should be roughly equal in specificity (don't mix "Step 1: Start" with "Step 2: Calculate the Fourier transform of the input signal").
- Works great for: algorithms, historical timelines, experimental procedures, decision trees.

### 6. Error Spotting

**`"type": "error_spotting"`**

Present a text with embedded errors. The student taps/clicks to identify each one.

```json
{
  "id": "error-1",
  "type": "error_spotting",
  "prompt": "Identify the errors in reasoning in the following argument:",
  "order": 6,
  "content": "We should not trust Dr. Smith's opinion on climate policy. He went to college in Europe, and European policies are always too strict.",
  "errors": [
    {
      "id": "err-1",
      "description": "Ad Hominem — dismissing the argument based on where Dr. Smith studied.",
      "hint": "Is the location of someone's education relevant to the validity of their argument?",
      "correction": "Evaluate Dr. Smith's arguments on their merits, not his background."
    },
    {
      "id": "err-2",
      "description": "Hasty Generalization — 'European policies are always too strict' is a sweeping claim.",
      "hint": "Can you generalize about all European policies?",
      "correction": "Provide specific examples of strict policies rather than generalizing."
    }
  ],
  "explanation": "This argument contains an ad hominem and a hasty generalization."
}
```

| Field | Type | Description |
|-------|------|-------------|
| `content` | string | The text containing errors. Use `{ERROR:0}`, `{ERROR:1}`, etc. to mark error positions. |
| `errors` | ErrorDef[] | Definitions for each error. |
| `errors[].id` | string | Matches the `{ERROR:N}` marker index. |
| `errors[].description` | string | Explains what's wrong. Shown after the student identifies the error. |
| `errors[].hint` | string | Hint for finding this error. |
| `errors[].correction` | string | How to fix the error. |
| `explanation` | string | Summary shown after completing the exercise. |

**Note:** The `{ERROR:N}` markers in `content` are replaced in the UI with tappable highlights. The N corresponds to the error's position in the `errors` array (0-based).

**Tips:**
- 2-4 errors per exercise.
- Errors should be *subtle but learnable* — not typos, but reasoning flaws, factual mistakes, or logical fallacies.
- Each error's `description` should *teach* — explain why it's wrong, not just that it's wrong.

## Assessments

An assessment is a final quiz at the end of the module. It references existing exercises by ID.

```json
"assessment": {
  "title": "Final Assessment",
  "passingScore": 0.7,
  "exercises": [
    { "exerciseId": "mcq-1", "weight": 1.0 },
    { "exerciseId": "mcq-2", "weight": 1.5 },
    { "exerciseId": "socratic-ai-1", "weight": 2.0 }
  ]
}
```

| Field | Type | Description |
|-------|------|-------------|
| `title` | string | Assessment title. |
| `passingScore` | float | 0.0-1.0. Default: 0.7 (70%). |
| `exercises` | AssessmentExercise[] | References to exercises. |
| `exercises[].exerciseId` | string | Must match an exercise `id` in the module. |
| `exercises[].weight` | float | Relative weight. Higher = contributes more to score. |

**⚠️ `exerciseId` must reference an exercise that exists in one of the module's sections.** Don't create standalone assessment exercises — reference existing ones.

**Tips:**
- Weight harder/more important exercises higher.
- Include a mix of exercise types.
- 5-10 questions is a good length.
- `passingScore` of 0.7 (70%) is the default. Adjust based on difficulty.

## Flashcards

Flashcards are reviewed via spaced repetition (FSRS algorithm). The app tracks when each card is due for review.

```json
"flashcardDeck": {
  "title": "Key Terms",
  "cards": [
    {
      "id": "fc-1",
      "term": "Deductive Reasoning",
      "definition": "Reasoning from general premises to a specific, guaranteed conclusion.",
      "context": "All mammals have lungs. Dolphins are mammals. Therefore, dolphins have lungs."
    }
  ]
}
```

| Field | Type | Description |
|-------|------|-------------|
| `title` | string | Deck title. |
| `cards[].id` | string | Unique within the deck. |
| `cards[].term` | string | Front of the card — the term or concept. |
| `cards[].definition` | string | Back of the card — the explanation. |
| `cards[].context` | string | Optional example sentence. Shown as a hint. |

**Tips:**
- Aim for 8-20 cards per module.
- Terms should be the *most important vocabulary* a student should retain long-term.
- `context` should be a concrete, memorable example — not another definition.
- Keep definitions to 1-2 sentences.

## Content Best Practices

### Section Structure

A well-designed section follows this pattern:

1. **Lesson** — teach the concept (reading material)
2. **Worked Example** — walk through an example step-by-step
3. **MCQ** — check basic understanding
4. **Socratic/Socratic AI** — test deeper comprehension
5. **Error Spotting or Drag Sequence** — apply knowledge

Not every section needs every type, but **every section should have at least 2 exercises**.

### Progressive Difficulty

Within a section, exercises should progress:
- **Recall** (MCQ) → **Comprehension** (Socratic) → **Application** (Error Spotting, Drag Sequence)

### Socratic AI Design Principles

1. **The prompt should NOT contain the answer.** Ask about implications, mechanisms, or "what would happen if" scenarios.
2. **`mustInclude` concepts should be multi-word phrases**, not single vocabulary words. They represent *understanding checkpoints*.
3. **Test the exercise yourself:** Can you pass it without knowing the topic? If yes, redesign.
4. **Use `"validationMode": "embedding"`** for conceptual questions. The keyword fallback is there for factual questions on devices without ML support.
5. **Set `minScore` between 0.5 and 0.7.** Lower = too lenient. Higher = too strict for own-word answers.

### Worked Example Design

- The `missingPart` should be the **key insight** of the process, not a trivial blank.
- Provide 3-5 keyword variations to accept common phrasings.
- `hint` should point toward the answer without giving it away.

### General

- **Estimated time:** A 30-minute module ≈ 3 sections × 2 lessons × 5 min + exercises.
- **Exercise IDs:** Use a consistent naming scheme: `mcq-1`, `socratic-2`, `drag-1`, etc.
- **Markdown in lessons:** Keep formatting simple. The mobile renderer supports bold, italic, headings, lists, and code. No tables, no HTML.

## Publishing a Module

### 1. Create your module directory

```
modules/your-course-id/module.json
```

### 2. Write `module.json`

Follow the schema above. Validate your JSON:
```bash
python3 -m json.tool modules/your-course-id/module.json > /dev/null
```

### 3. Calculate the SHA-256 checksum

```bash
sha256sum modules/your-course-id/module.json
```

### 4. Add entry to `modules.json`

```json
{
  "id": "your-course-id",
  "title": "Your Course Title",
  "description": "What students will learn.",
  "author": "Your Name",
  "version": "1.0.0",
  "estimatedMinutes": 60,
  "checksum": "sha256:THE_HASH_FROM_STEP_3",
  "downloadUrl": "https://raw.githubusercontent.com/DuaneJaspers/learning-modules/main/modules/your-course-id/module.json"
}
```

### 5. Verify and submit

- Check that all `exerciseId` references in `assessment` exist in the module.
- Check that `correctOrder` indices in `drag_sequence` exercises are valid (0-based, no duplicates).
- Check that `{ERROR:N}` markers in `error_spotting` content match error indices.
- Open a pull request. CI will validate the index checksums automatically.

## Common Pitfalls

| Pitfall | Fix |
|---------|-----|
| `correctIndex` is 1-based | It's **0-based**. First option = index 0. |
| `correctOrder` uses item IDs | Use **0-based indices** into the `items` array. |
| `mustInclude` concepts are single words from the prompt | Use **multi-word comprehension checkpoints**. See [Socratic AI section](#4-socratic-ai-embedding). |
| `exerciseId` in assessment doesn't match any exercise | Must reference an existing exercise `id` from a section. |
| Forgetting to bump `version` after content changes | Always bump version so the app shows the Update button. |
| Forgetting to update checksum in `modules.json` | Recalculate with `sha256sum` after any change to `module.json`. |
| `type` field doesn't match Kotlin discriminator | Must be exactly: `mcq`, `worked_example`, `socratic`, `socratic_ai`, `drag_sequence`, `error_spotting`. |
| Markdown in `content` has raw newlines | Use `\n\n` for paragraph breaks within JSON strings. |
| Too many mustInclude concepts (6+) | Aim for 3-5. More than 5 makes the exercise impossibly strict. |
| `minScore` too high (>0.8) | Students expressing in their own words will naturally miss some. 0.5-0.7 is the sweet spot. |
